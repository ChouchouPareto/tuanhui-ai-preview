## 优化方案与固定边界

上一版问题不只是表单样式：上方文字与下方字段形成两个事实来源，修改上方后没有重新整理；规则无法识别的内容又让用户重填。

本版固定为：原框输入 → 整理摘要 → 仅补未确定内容 → 确认费用与生成。

- 首页原输入框是唯一文字入口，下方只读摘要，不再提供第二套店名、菜品、价格、卖点表单。
- 点击上方发送会重新整理当前文字，而不是只滚动到旧摘要。
- 编辑全文采用 replace，不继承上一次未确认创作里的旧字段；已确认项目记忆仍可复用。
- 点击问题回到同一个输入框，标明正在回答什么；reply 合并原需求，保留其余事实。取消补充恢复原文。
- 文字、素材、模型、风格、待上传状态、补充状态发生变化，旧摘要不能直接生成；重新整理后需要重新确认费用。
- 生成按钮只确认用户已经看到的快照，不在按钮内部悄悄重写需求或重新理解。
- 专业创作保留原有流程；装修全案、订阅积分、自动赔付不属于本轮。

## 理解能力与安全边界

默认规则覆盖明确标签和常见表达，例如“我的店叫山城酸菜鱼，主推酸菜鱼双人餐，99元，不展示价格”。不把规则声称为通用自然语言理解。

复杂描述提供折叠的文字智能理解选项，默认关闭，需单独同意本次模型费用。复用现有百炼文本调用适配器，只发送文字。模型结果须能回指原文子串，不能凭空新增事实；歧义继续补问。

每个创作修订的理解调用有稳定任务键，已成功结果可复用；处理中、超时或未知结果不会自动再次请求。生成仍需独立确认。当前是调用次数控制，不是已上线的积分扣费或金额报价系统；真实模型效果与账单未在本轮验证。

门头不能进入成品，真实菜品图仍是本阶段生成的必要素材。纯文字可以整理需求，但不等于已支持无实拍素材的完整生图场景。OCR、复杂否定和任意口语仍需专项样本验收。

## 实现契约

- IntakeInput 新增 input_mode（merge / replace / reply）、reply_field、accepted_understanding_policy。
- 旧客户端默认 merge；新首页用 replace / reply。新快照 schema_version=2；旧快照恢复后须重新整理。
- 前端输入指纹和后端 revision / snapshot_hash 双重约束，确认只提交已展示版本。
- 理解任务复用 WorkflowTask、ModelCallRecord；无新增数据库迁移。
- 网络/确认异常不提供会隐式新建创作的通用“重新整理”按钮，用户可查看原需求并明确选择下一步。
