# 团绘AI · Input—Output 完整PE工程与类目架构审核 v0.10.1

文档日期：2026-09-12。核对基线：代码提交 ede1a9a（运行版本 v0.10.0 / region-master-v3）。

本文件是完整工作流的现状审计与下一版架构设计，不表示所有规划已开发。v0.10.1 是文档版本，不是已上线功能版本。保留 v0.10.0 原稿与历史备份，不覆盖。

## 1. 先回答：前一份文档是什么

《构图模板与PE审核_v0.10.0.md》是多轮讨论后，**构图模板和实际生图提示词的阶段性实现结果**，不是完整产品PE总纲，也不是全部约束均已落地的证明。

已落实的核心方向：20:3整图设计后裁切；模板区域不等于导出切片；门头资料与可入画素材区分；克制文案；模板库选型；整体风格一致；独立水印导出。

没有完成的部分：多行业/二级类目路由、独立创意文案模型、案例检索、模板美术验收、全类型生成与全案调度、生成后的自动语义质量检查。

当前代码仍明显餐饮化：理解器自称“餐饮设计需求整理器”，OCR只识别餐饮经营主体，默认视觉是餐具静物，文案默认“发现你的下一餐”。**不能将它当作已支持丽人、休闲娱乐、购物的通用系统。**

## 2. 分类框架：行业、输出类型、模板应分开

| 维度 | 回答的问题 | 示例 | 当前状态 |
|---|---|---|---|
| 行业一级类目 | 商家做什么生意？ | 餐饮、丽人、休闲娱乐、购物 | 尚无统一分类表与路由 |
| 行业二级类目 | 具体是哪种经营场景？ | 餐饮—地方特色菜、火锅、烧烤、酒吧、轻餐 | 仅有少量关键词创意分支，不是真正二级类目 |
| 输出类型 | 需要交付什么图？ | 五连图、Logo、代金券主图 | 已登记规格；现有一键入口仅五连图 |
| 经营/营销目标 | 本次希望突出什么？ | 品牌展示、套餐介绍、活动推广 | hero_item / selling_points 等字段承载，未独立建模 |
| 素材策略 | 哪些资料用于识别，哪些可以入画？ | 门头识别、产品实拍、AI示意 | 部分已实现，依赖素材角色正确 |
| 构图模板 | 画面各区域做什么？ | 左文右视觉、中置标题 | 12套原始区域规则，未完成美术验收 |
| 风格模板 | 用什么视觉语言？ | 品牌质感、清爽简约 | 4组风格预设，不是完整风格资产库 |
| 案例 | 为什么选择这种表达？ | 同行业同输出类型的优秀作品拆解 | 未接入自动检索 |

结论：保留目前“输出规格与构图区分离”的优点，新增行业分类这一独立轴。不要把“火锅”“五图”“清爽”“左文右图”塞进同一模板分类。

### 2.1 下一版行业数据结构（设计，未实现）

采用稳定ID、可修改中文名称、别名、父级、启用状态、版本号；不能以显示名称作为程序唯一标识。示例：

```json
{
  "taxonomy_version": "industry-v1-draft",
  "primary_id": "food",
  "secondary_id": "food.hotpot",
  "primary_label": "餐饮",
  "secondary_label": "火锅",
  "source": "user_text",
  "evidence": "给我的火锅店做五连图",
  "status": "inferred",
  "confidence": null
}
```

餐饮可先登记地方特色菜、火锅、烧烤、酒吧、轻餐；这是用户给定的初始分类，不宣称是外部平台的官方分类。丽人、休闲娱乐、购物先有一级节点，二级节点后续补充。跨类目商家用一个本次主类目加多个标签，不在用户不知情时强改分类。

不要求用户先填写行业表单。能从文字/资料判断就内部路由；不确定二级类目时可用一级通用包。一级也不明时只能走行业中性方案，不能默认画菜。确实影响主体选择时，在原对话中问一个简短问题。

### 2.2 PE分层与装配（目标结构）

1. 通用事实、安全、素材使用和指令边界。
2. 一级行业PE：行业通用的对象、语气与风险点。
3. 二级类目PE：具体主体、场景、禁用错配元素。
4. 输出类型PE：母图比例、内容安全区、导出方式。
5. 本次目标与已确认商家事实。
6. 选定构图模板的区域职责。
7. 选定风格模板与品牌资料。
8. 少量匹配案例的抽象设计规则。
9. 模型适配约束与结构化输出契约。

上层事实/素材禁用规则不能被类目、案例或用户原文覆盖。硬性约束冲突时停止该方案并解释，不拼接相互矛盾的提示词。输出尺寸与安全区由程序验证，不只写在PE中。

二级类目包不存在时继承一级包；无匹配构图时改选支持该输出的通用构图，不凭空产生坐标。行业中性包和这些回退路由目前均待开发。

## 3. 输出标准与实际可用范围

| 输出类型 | 完整设计与导出标准 | 当前代码能力 |
|---|---|---|
| 团购首页·五连图 | 20:3母图，导出5张4:3 | 主流程已接入；本地4000×600，切片800×600 |
| 团购首页·三连图 | 12:3母图，导出3张4:3 | 规划/本地裁切可复用；入口和供应商尺寸适配未完成 |
| 团购首页·首页装修图 | 上传单元4:3；整体结构待确认 | 未配置，不自动猜尺寸 |
| Logo | 4:3画布；核心内容限定1:1 | 仅规格登记；目前按居中1:1记录，位置可再确认 |
| 套餐主图 | 同Logo安全区；装饰可以超出1:1 | 仅规格登记 |
| 代金券主图 | 同Logo安全区；金额、条件来自真实资料 | 仅规格登记 |
| 菜品单品图 | 4:3；与推荐菜合并 | 仅规格登记 |
| 详情页 | 最终上传单元4:3；整体页数与拼接结构待确认 | 未配置 |
| 团购宣传图 | 4:3 | 仅规格登记 |

全案不是第十种图片格式，而是组合任务。默认：代金券主图＋五连图＋Logo；其他类型单独选配。当前只有默认组合常量，没有完整调度、逐项计费和失败补偿。

五连图和三连图的裁切是最后的导出动作，不把20:3母图强制划为五个独立设计区。后续可以增加非渲染的裁切预检线，检查文字是否被切断；预检线不入画，也不能重新变成五套重复海报。

## 4. 当前 Input—Output 实际工作流

| 环节 | 实际输入 → 处理 → 输出 | 调用/约束位置 |
|---|---|---|
| 01 输入 | 一句话、上传照片、已有项目资料 → 保存草稿/素材 → 本次创作 | page.tsx / m1-review.tsx |
| 02 理解 | 当前及累计文字 → 规则提取，非空文字可调用理解模型 → 有来源的5类事实、待澄清字段 | intake.py / intake_understanding.py |
| 03 图片资料分析（独立分支） | 指定角色图片 → OCR＋事实整理 → 事实候选/视觉观察/证据 | analysis.py / model_gateway.py / schemas.py |
| 04 就绪判断 | 事实＋素材角色＋展示选项 → 条件校验 → ready 或对话提问 | compile_intake / evaluate / conversation_reply |
| 05 授权与快照 | ready＋本次授权 → 版本/哈希/素材所有权/worker检查 → 冻结方案、幂等任务 | creation_api.confirm |
| 06 设计规划 | 冻结事实、风格、素材数 → 输出规格＋模板选择＋规则文案 → region-master-v3方案 | design_plan.py / layout_catalog.py |
| 07 生图PE装配 | 通用生图PE＋文案PE＋选定区域＋本次资料＋素材模式 → 一条实际生图prompt | build_visual_prompt |
| 08 付费前预检 | 方案、素材、本地试排 → 模板/容量/文件检查 → 允许调用或错误 | run_generation |
| 09 图片模型 | 实际prompt → 默认千问，当前主流程一次尝试 → 无正文视觉底图 | call_qwen / worker.py |
| 10 本地成图 | 底图＋可用实拍＋规则文案 → 模板区域排版 → 完整母图 | compose_regions |
| 11 导出 | 母图 → 平台可见水印层 → 原图与4:3切片两套文件 | render_and_slice |
| 12 展示恢复 | 文件清单＋任务结果 → 预览/独立下载/项目恢复 → 继续创作 | generation-gallery / project workspace API |

关键区别：本系统当前不是一个自由循环执行的设计Agent。文字理解、素材OCR、生图是不同调用；对话回复仍是规则句式；主文案仍是规则候选；并没有一个“聪明AI”贯穿规划、写作、审图和反思重画。

### 4.1 当前模型与调用边界

以下是代码默认配置名，不等同于供应商最新可用性，也不保证环境变量没有覆盖。实际任务应以ModelCallRecord为准。

| 用途 | 代码默认模型/方法 | 实际能力边界 |
|---|---|---|
| 文字理解 | qwen3-vl-plus，只传文字 | 提取store_name、hero_item、hero_price、positioning、selling_points；没有行业路由或创作执行工具 |
| 门头/环境观察 | qwen3-vl-plus | 独立素材分析分支；不是每次一键生图必定调用 |
| 菜单OCR | qwen-vl-ocr-2025-11-20 | 逐图识别；菜单强事实需核对 |
| OCR结果事实整理 | qwen3-vl-plus | 汇总资料；不是设计模型 |
| 生图 | qwen-image-3.0 | 当前请求尺寸2000×300，1张；后续本地成为4000×600，不是模型原生4000像素细节 |
| 可选豆包生图 | doubao-seedream-5-0-260128 | 配置入口存在；当前oneclick worker不自动失败切换 |
| 文案创作、选模板、排字 | 当前为本地规则/PIL | 没有独立LLM文案或美术排字调用 |

千问请求设置prompt_extend=true、enable_thinking=true；这只是传给供应商的参数，不代表已经实现应用层深度循环理解。返回图也不保证精确遵守区域，需要后续视觉验收。

### 4.2 当前数据传递的事实层

- 项目已确认FactVersion → 本次旧snapshot → 当前提取事实 → 显式answers，逐层合并。
- AI提取的value必须位于quote中，quote必须位于输入文字中；uncertain_fields不采用为确定事实。
- snapshot保存facts、sources、assets、render_mode、show_price、show_store_name、style、gaps和ready。
- 目前facts来源粒度多为user_text/project_confirmed，不是每项都带完整定位证据；原始OCR证据另存。
- 当前compile_intake只从已确认项目资料带入5类事实及品牌色，restaurant_category与完整视觉观察没有形成通用行业路由。
- creative_direction.category只是关键词视觉联想，不是已确认的商家行业，更不能作为真实菜单。

### 4.3 素材真实边界

已知角色为门头/菜单/环境的素材是recognition_only，不送给图片模型，也不由本地成图函数放入成品。真实产品路径当前仅接纳product类型且角色为dish/signature_dish的素材。

但上传入口chooseFiles依入口给照片赋storefront或dish角色，**尚无通用自动素材分类前置闸门**。用户把门头传进产品入口时，可能被错标为dish；现有“门头不入画”依赖角色正确，不能宣称全链路已经绝不会错。

门头OCR的自报置信度与文字证据校验可以减少错认，但不能保证100%正确。相邻多家店、缺字、低置信度保留候选；必要时只核对店名，不让用户重填整份需求。环境图是否允许直接入画尚未确认，现阶段按资料处理。

真实照片目前是本地等比放进视觉区，未实现抠图、主体分割、智能融合。生图请求实际references=[]，不会自动把用户全部照片发给图片模型。Logo观察线索不是透明Logo文件，不能据此承诺高保真复刻。

### 4.4 当前强制条件与容易卡住的位置

| 条件 | 当前行为 | 应保留还是优化 |
|---|---|---|
| 完全无文字且无素材 | 不能开始 | 保留，用一句自然提示 |
| 缺店名 | 一键模式可不展示，不一律必填 | 保留可选；专业旧入口仍有必填，需单独统一 |
| 无菜名/卖点 | 有店名的AI示意可做品牌主题；可用实拍也能素材驱动 | 不恢复所有字段必填 |
| 无实拍 | 新一键允许示意；拒绝示意时需要可入画素材 | 保留用户选择，不强造真实产品 |
| 要展示价格但没有有效价格 | 追问或不展示 | 价格真实约束保留，不能猜 |
| 模糊/冲突表达 | 正则检测“或”等，可能误伤正常文案 | 需语义冲突判断，不靠单字拦截 |
| 非空文字理解失败 | 目前可能阻断本次提交 | 需提供明确降级/恢复动作；不自动重复付费 |
| AI理解授权 | use_ai要求policy值 | 保留费用知情，但不当成业务字段追问 |
| 生图授权 | confirm要求材料授权、预算策略、版本和哈希 | 后端必须校验；前端同次授权后ready可自动提交，不必再次点确认 |
| 页面重进/新任务 | 授权存于页面ref，可重置 | 需明确授权有效范围，不能静默永久扣费，也不重复询问同次业务事实 |
| 缺失/篡改素材、任务过期、worker未就绪 | 拦截且保留资料 | 保留系统安全检查，并区分用户补信息与系统故障 |
| 旧专业分析coverage_for | 仍检查店名/定位/主推/卖点/价格等 | 不可把旧专业流程强行套回一键入口 |

当前问答生硬不是单纯少了一条“语气自然”的PE，而是conversation_reply仍以固定条件拼句；增加生图提示词不会修复这一层。

## 5. 当前生图PE到底怎样组装

```text
prompts/generation_v3.md（整体画面/素材/文字层边界）
+ canvas.ratio
+ plan.layout（只注入选中的1套，不是12套全文）
+ prompts/copywriting_v1.md
+ JSON任务资料（locked_facts、copy、style、text_color、creative_subject、brand_references）
+ render_mode分支（只生成背景供真实图本地排版 / 生成主题示意静物）
= 发送给生图模型的prompt
```

图片模型当前被要求不绘制正文。文案PE虽然加入生图prompt，但候选文字已经由build_design_plan决定，**不能因此说实现了独立创意文案生成**。改文案质量需要改前面的规划/文案环节，而不只是往生图prompt加更多形容词。

原PE写有“可编辑的本地文字层”，准确含义是保留文案数据后可重新排字；当前交付仍是栅格PNG，不代表已提供可直接编辑文字图层的画布或PSD/SVG导出。

当前模板选择：按输出类型过滤，再按真实素材数量过滤视觉槽数，最后按店名或主推内容的稳定哈希选择。不是按行业、营销目标、文字长度、案例相似度做设计判断。模板是12套区域骨架，不是12套经过案例拆解和美术验收的成熟作品。

实际成图顺序是整图生成→本地合成/排字→导出裁切；历史v2兼容分支仍在，含旧五场景和底部渐变，不应与新v3混读。新创作使用v3，旧作品不会自动重做。

## 6. 建议的下一版完整工作流（设计，未实施）

1. 输入归一化：一句话/照片/项目记忆统一接入，保留原始资料与用户修改顺序。
2. 资料判别：识别一级/二级类目、输出类型、素材角色、是否要求真实产品；不把推测变成商业事实。
3. 形成需求摘要：明确事实、可创意项、待确认项分开。只有影响正确出图的冲突才追问。
4. 路由行业PE：通用→一级→二级；未知行业不默认餐饮。
5. 匹配输出规格与素材策略：缺非必要信息则省略；缺必要金额/套餐组成则简短追问或换品牌主题方案。
6. 检索构图/风格/案例：先按输出兼容性、行业、素材数量、文字容量筛选，再按设计匹配度选择；只加载本次需要的规则。
7. 创意文案生成与校验：创作表达但不创造事实；输出主副标题、事实引用、风险标记、长度。
8. 设计计划冻结：保存行业、输出类型、模板与风格版本、素材角色、文案、授权和预算。
9. 模型适配：将抽象计划转成具体模型支持的尺寸和prompt；不把画布尺寸、原生模型尺寸、导出尺寸混为一谈。
10. 生成与合成：保留完整母图原则；针对真实主体决定局部合成或授权参考生成，不能偷偷改素材用途。
11. 验收：主体类别、模板角色、门头禁用、事实文字、比例、安全区和裁切；未通过不标为高质量成品。
12. 导出与恢复：可见水印选择、完整母图与切片、项目版本、用量与失败记录。

应用层可以增加“理解→校验→修正”的有限循环，但不是无限思考或无限重新生图。每类循环应有次数、费用上限、停止条件和用户可见状态。超限后保留已完成内容，不自动赔付或加收费用；这些商业规则另行定义。

## 7. 案例与模板整理：按要求进入Figma

后续实际整理构图/风格模板时，必须调用Figma，在独立文件中整理；本轮只做现状审计和工程分类说明，没有新建或修改模板，也没有声称已创建Figma文件。

建议独立文件名：团绘AI｜模板与案例库。每个模板ID在Figma、工程JSON和PE引用中一致。

- 分类索引：一级/二级行业、输出类型、风格、使用场景。
- 原始参考页：原图、来源、授权信息；不把参考商家的名称、价格、销量带入新用户事实。
- 案例拆解页：主体、文案层级、色彩、区域职责、可复用设计规律与禁用误抄信息。
- 构图模板页：真实比例母图、归一化坐标、区域允许元素；裁切预检线单独图层且不导出。
- 风格模板页：颜色、字体规则、材质、光影、装饰语言。
- 验收页：不同素材/行业样张、通过与失败例、修改记录、发布版本。

每条案例记录应有case_id、industry_ids、output_types、layout_id、style_id、source、rights_status、facts_to_exclude、design_rules、figma_node、status。只发布通过审核的设计规则；不将整个案例库塞进每次prompt。

PE负责规则表达，程序负责确定性约束，模板负责区域与风格，案例负责设计依据。Skill可封装“案例拆解/模板验收”的制作流程，但给文件起名Skill不会自动使后端具备调用、检索和评测能力。

## 8. 验收与用量：不要再只看接口成功

| 测试输入 | 目标结果 | 当前差距 |
|---|---|---|
| 袁记云饺，五图 | 明确主题后能走通，无菜名不反复索取 | 现有短句/示意路径支持；无完整视觉验收 |
| 美甲店，做主图 | 丽人PE与对应主体，不出现餐具 | 行业路由和主图入口尚未实现 |
| 火锅店，没有照片 | 可做明确示意，不能伪造套餐和优惠 | 餐饮示意支持，二级PE未实现 |
| 只有门头 | 自动判为识别资料，绝不当产品照片 | 目前依角色过滤，上传自动判别缺失 |
| 只发产品实拍 | 保留主体，少问无关信息 | 餐饮角色可用；通用产品识别未实现 |
| 代金券，没有金额 | 询问金额/条件或切换非券设计 | 对应入口未实现 |
| 不放店名、不放价格 | 按用户选择省略，不制造缺项 | 一键已有相关处理；需语义回归集 |
| 三连图 | 12:3整图→3张4:3 | 本地链路可复用，端到端未开放 |
| 多邻店门头/模糊字 | 展示候选或核对，不猜 | OCR有证据校验；仍需真实图片评测 |
| 长文案与复杂画面 | 不截断事实，不与主体冲突 | 有容量预检，缺语义/美术检查 |

当前有模板/比例/容量/素材等程序测试，但generation-audit显式记录semantic_visual_review=not_automated。即使返回成功，也不能说明“类目正确、画面好看、门头被正确分类”。

当前文字理解记录prompt_tokens与completion_tokens；OCR/事实整理记录返回用量；图片调用记录模型、耗时、状态，但没有完整标准化图片用量/价格核算。不能凭字符数给出准确金额。

效能优化顺序：先减少错误分流与重复追问，再压缩上下文，再减少重复模型调用。目标采用事实增量记忆、按图哈希缓存OCR、按版本缓存PE包、每次只注入一个模板与少量案例；这些缓存和预算路由尚未全部开发。

## 9. 开发优先级与商家后台

优先级1：打通行业分类与未知类目回退、素材自动判别、减少固定句式与错误追问。这比继续堆更多餐饮提示词更基础。

优先级2：在Figma完成首批模板/案例可视化拆解与审核，再发布工程规则；建立文字与视觉验收集。

优先级3：独立文案生成/校验、模板匹配、模型适配与用量统计。

优先级4：扩展各输出类型与全案编排，而不是一次性开放未验收入口。

商家侧需要轻量工作台，但不必现在另起复杂后台：现有“我的项目/素材库”可以承载门店资料、品牌素材、历史作品、生成进度，后续补额度/账单与反馈即可。

平台内部管理端是另一件事：需要维护行业树、PE版本、模板发布、案例授权、任务失败和用量。建议先保证文件版本化和审核流程，再做管理UI；本轮不擅自开发新后台，也不把未实现的订阅积分/赔付写成上线能力。
